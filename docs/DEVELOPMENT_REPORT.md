# Отчёт о разработке FlowTrack Personal

## Назначение документа

Этот документ фиксирует историю создания FlowTrack Personal, ключевые
архитектурные решения, подтверждённые проблемы, выполненные исправления и
текущее состояние проекта.

Отчёт обновлён 30 июля 2026 года по:

- обсуждению проекта и пользовательским отзывам;
- текущему исходному коду;
- истории Git;
- миграциям Cloudflare D1;
- опубликованной версии 21;
- автоматическим и ручным проверкам.

Под «реестром ошибок» ниже понимаются подтверждённые проблемы, сохранившиеся в
истории разработки. Рабочая бета-версия всё ещё может содержать невыявленные
дефекты.

## 1. Исходная задача

Целью было создать единое приложение личной продуктивности для собственного
использования, а затем подготовить его к безопасному использованию членами
семьи.

В основу анализа вошли два прототипа:

1. `all-in-one-productivity-application` — функциональная основа;
2. `glm 5.2` — более удачный, по оценке пользователя, референс интерфейса и
   механики.

Было решено не выбирать один прототип целиком, а объединить сильные стороны:

- сохранить набор функций первого проекта;
- перенести визуальную лёгкость и удобство второго;
- самостоятельно переработать канбан, таймер, заметки, обмен JSON и хранение
  данных;
- сначала сделать продукт удобным для владельца;
- затем добавить личные кабинеты, защиту данных и мобильные сценарии;
- после накопления данных замкнуть цикл «план → выполнение → анализ».

## 2. Итоговая архитектура версии 21

FlowTrack стал full-stack приложением:

- React 19 и Next.js 16 для интерфейса;
- TypeScript во всех основных слоях;
- Vinext, Vite и Cloudflare Worker для сборки и запуска;
- Cloudflare D1 для постоянного хранения;
- Drizzle ORM и версионируемые SQL-миграции;
- Sign in with ChatGPT для идентификации;
- отдельные роли `owner` и `member`;
- серверная изоляция данных по пользователю;
- ChatGPT Sites для публикации;
- событийная история для достоверной аналитики.

Основные данные изменяются через защищённый `/api/data`. Аналитический снимок
рассчитывается отдельным `GET /api/analytics`. Оба маршрута самостоятельно
определяют текущего пользователя и не принимают произвольный `userId` от
клиента.

### Единая модель задачи

Задачи расписания и карточки канбана объединены в одну сущность. Положение
задачи на доске хранится в `kanbanColumnId` и `kanbanOrder`, а перенос между
колонками синхронизирует статус `todo`, `doing` или `done`.

### Настройки устройства

Тема, акцент, масштаб, режим боковой панели, стартовый раздел и анимации
хранятся в `localStorage` текущего устройства. Они применяются до первого
отрисованного кадра, чтобы избежать вспышки неправильной темы.

### Событийная аналитика

Миграция `0004_nappy_songbird.sql` добавила:

- `analytics_events`;
- `analytics_tracking`;
- индексы по пользователю, типу, сущности и дате;
- 13 SQLite-триггеров.

Миграция восстанавливает доступную базовую историю из текущих задач, привычек и
завершённых записей времени. Проекты для подписей и цветов читаются из основной
таблицы. После установки триггеры точно фиксируют завершения, повторные
открытия, переносы сроков, удаления, восстановления, отметки привычек и
фокус-сессии.

## 4. Основные этапы разработки

### Этап 1. Анализ и первая сборка

Определены основные разделы: обзор дня, привычки, расписание, проекты, таймер,
заметки и цели. Созданы единая визуальная система, адаптивная навигация и
серверное хранение.

На этом этапе приложение было ориентировано на одного пользователя, а канбан
ещё не имел полного перетаскивания.

### Этап 2. Рабочий канбан

Подключён `dnd-kit`, добавлены:

- отдельные ручки для колонок и карточек;
- мышь, сенсорное управление и клавиатурный датчик;
- оптимистичное изменение интерфейса;
- API сохранения порядка колонок;
- API переноса карточек;
- синхронизация статуса после переноса.

### Этап 3. Переработка интерфейса

После повторного анализа `glm 5.2` изменены:

- светлая палитра;
- визуальная иерархия;
- карточки, отступы и состояния;
- расписание;
- кнопки добавления;
- модальные окна;
- мобильная компоновка.

Одновременно исправлена геометрия `DragOverlay`.

### Этап 4. Расширение продуктивности

Добавлены:

- свободный таймер;
- полноценный Помодоро;
- сохранение фазы и времени на сервере;
- редактор TipTap;
- списки, чек-листы, цитаты, код и ссылки;
- полная резервная копия `flowtrack-backup`;
- восстановление данных из JSON.

### Этап 5. Безопасное планирование

Полная резервная копия отделена от плана:

- `flowtrack-backup` заменяет весь набор данных;
- `flowtrack-plan` добавляет новые записи.

Появились предварительный просмотр, проверка ссылок, пропуск совпадений,
автоматическая копия перед импортом, журнал импортов и отмена. Также добавлены
быстрое создание, глобальный поиск, «Входящие», повторяющиеся задачи и корзина.

### Этап 6. Многопользовательская модель

Добавлены:

- таблица `users`;
- вход и выход через ChatGPT;
- отдельный кабинет для каждого email;
- поля `userId` и индексы;
- фильтрация операций по текущему пользователю;
- перенос старых записей без владельца первому пользователю;
- роли `owner` и `member`.

### Этап 7. Стабилизация после реального использования

Версии 7–11 исправили реальные сценарии:

- финансовые цели больше миллиона;
- случайный выход через мобильный профиль;
- блокирующие D1-операции на холодном запуске;
- бесконечную загрузку без восстановления;
- неверное назначение владельца;
- фиксированное имя в приветствии.

### Этап 8. Производительность и работа с длинными заметками

Версии 13–15 вынесли TipTap из начального пакета и последовательно улучшили
редактор:

- динамическая загрузка только при открытии заметки;
- закреплённая панель форматирования;
- автосохранение после короткой паузы;
- локальная копия черновика;
- повтор после возвращения сети;
- защита при закрытии и перезагрузке;
- явные состояния сохранения;
- полноэкранный режим и статистика текста.

### Этап 9. Персонализация

Версии 16–17 добавили настройки на уровне устройства:

- три масштаба;
- системную, светлую и тёмную темы;
- пять акцентных цветов;
- развёрнутую, компактную и автоматическую боковую панель;
- выбор стартового раздела;
- системные, полные и минимальные анимации;
- сброс настроек.

Масштаб построен на дизайн-токенах, а не `zoom` или `transform`, чтобы не
нарушать положение курсора, модальных окон и drag-and-drop.

### Этап 10. Мгновенные действия и мобильная структура

В версии 18 календарь привычек переведён на оптимистичное обновление. Раньше
клик ожидал запись и повторную загрузку всего набора данных. Теперь отметка
показывается сразу, сервер подтверждает целевое состояние в фоне, а при ошибке
интерфейс откатывается.

В версии 19 нижняя мобильная навигация сокращена до четырёх основных разделов и
кнопки **«Ещё»**. Вторичные разделы, настройки и действия собраны в отдельной
нижней панели. Поиск и профиль вынесены в шапку; добавлены безопасные зоны,
мобильные модальные окна и корректное положение уведомлений.

### Этап 11. Аналитика

Версия 20 добавила:

- неделю, месяц, квартал и год;
- переход между периодами;
- сравнение с предыдущим календарным периодом;
- фильтр проекта;
- выполнение плана;
- выполнение в срок;
- фокус-время;
- регулярность привычек;
- завершённые, незавершённые и перенесённые задачи;
- график «план / факт»;
- результаты по проектам;
- календарь активности;
- алгоритмический итог.

Перед построением интерфейса проведён аудит данных. Было установлено, что
завершения, отметки привычек и фокус-сессии можно восстановить, а прежние
переносы сроков и повторные открытия ранее не фиксировались. Поэтому
исторические значения не подменяются предположениями: миграция восстанавливает
только доступные факты, а точный учёт новых событий начинается с версии 20.

### Этап 12. Актуализация живой аналитики

В версии 21 расчёт отделён от простого хранения событий. Перед построением
снимка FlowTrack сопоставляет события с существующими активными задачами,
привычками, проектами и записями времени. Удалённые источники больше не создают
устаревшие показатели, а восстановление записи возвращает её вклад. Клиент
автоматически запрашивает новый снимок после изменения основных данных и даёт
отдельную кнопку **«Обновить данные»**.

## 5. Реестр обнаруженных проблем и исправлений

### FT-01. Канбан нельзя было перетаскивать

**Симптом:** колонки и карточки нельзя было перемещать, статус приходилось
менять вручную.

**Причина:** первая версия отображала доску без полного drag-and-drop цикла и
серверного сохранения порядка.

**Исправление:** подключены сенсоры `dnd-kit`, `SortableContext`, зоны сброса,
оптимистичное состояние и действия `reorderKanbanColumns` /
`reorderKanbanCards`.

**Статус:** исправлено в версии 2.

### FT-02. Карточка улетала дальше курсора

**Симптом:** визуальная копия карточки или колонки смещалась относительно
указателя.

**Причина:** `DragOverlay` находился внутри преобразованного контейнера и
получал другую систему координат.

**Исправление:** overlay перенесён через portal в `document.body`, добавлено
выравнивание по точке захвата и отключена лишняя анимация сброса.

**Статус:** исправлено в версии 3.

### FT-03. Первая визуальная версия была слишком тяжёлой

**Симптом:** функциональность устраивала, но стиль и механика `glm 5.2`
воспринимались удобнее.

**Причина:** первая версия была собрана вокруг функций и унаследовала более
тяжёлую подачу.

**Исправление:** переработаны палитра, плотность, карточки, расписание, кнопки,
отступы и мобильная компоновка.

**Статус:** улучшено в версии 3.

### FT-04. Риск расхождения задачи и канбан-карточки

**Симптом:** запись расписания и карточка проекта могли получить разные
статусы.

**Причина:** ранняя модель хранила `tasks` и `kanban_cards` отдельно.

**Исправление:** задача стала единой моделью с `kanbanColumnId` и
`kanbanOrder`; для старых данных сохранён `legacyCardId`.

**Статус:** исправлено в версии 5.

### FT-05. Импорт плана мог заменить текущий кабинет

**Симптом:** пользователь хотел добавлять созданный ChatGPT план, не стирая
текущие данные.

**Причина:** существовал только сценарий полного восстановления.

**Исправление:** введён `flowtrack-plan` с проверкой, предпросмотром, добавлением
новых записей, пропуском совпадений и отменой.

**Статус:** исправлено в версии 5.

### FT-06. Старые данные исчезли после добавления аккаунтов

**Симптом:** прежние записи не отображались в новом личном кабинете.

**Причина:** до версии 6 записи не содержали `userId`.

**Исправление:** добавлена миграционная логика назначения записей без владельца
первому созданному пользователю.

**Ограничение:** уже потерянные данные без резервной копии восстановить нельзя.

**Статус:** исправлено в версии 6.

### FT-07. Значок профиля неожиданно завершал сессию

**Симптом:** на телефоне нажатие на аватар сразу выводило пользователя.

**Причина:** значок был прямой ссылкой выхода, хотя выглядел как профиль.

**Исправление:** значок открывает профиль и настройки; выход вынесен в отдельное
подписанное действие.

**Статус:** исправлено в версии 8.

### FT-08. JSON отклонял финансовую цель

**Симптом:** импорт показывал `Некорректное число «goals[1].targetValue»`.

**Причина:** общий валидатор ограничивал число одним миллионом.

**Исправление:** для целей введён лимит `1 000 000 000 000` в обычном API,
backup и `flowtrack-plan`; добавлен регрессионный тест.

**Статус:** исправлено в версии 7.

### FT-09. Вечная загрузка приложения

**Симптом:** кабинет и админка могли бесконечно показывать загрузку.

**Причина:** подключение к D1 выполняло `CREATE TABLE`, `ALTER TABLE`, индексы и
`PRAGMA table_info` внутри пользовательского запроса.

**Исправление:** схема перенесена в SQL-миграции развёртывания; `getDb()` только
подключает Drizzle к готовой D1.

**Статус:** исправлено в версии 9.

### FT-10. Загрузка не восстанавливалась после сетевой ошибки

**Симптом:** индикатор не давал понятного действия.

**Причина:** запросы не имели общего ограничения времени и сценария повтора.

**Исправление:** добавлены 15-секундный тайм-аут, сообщение и кнопка
**«Повторить»**.

**Статус:** исправлено в версии 9.

### FT-11. Владелец не мог открыть `/admin`

**Симптом:** настоящий владелец видел отказ в доступе.

**Причина:** владельцем становился первый созданный профиль, включая тестовый.

**Исправление:** роль закреплена за `FLOWTRACK_OWNER_EMAIL` и сверяется при
входе.

**Статус:** исправлено в версии 10.

### FT-12. У всех было приветствие «Добрый день, Андрей»

**Симптом:** любой пользователь видел одно имя.

**Причина:** строка была временно записана в компоненте.

**Исправление:** используется первое имя профиля и местный час; при отсутствии
имени email не раскрывается.

**Статус:** исправлено в версии 11.

### FT-13. Риск просмотра общих данных разными пользователями

**Симптом:** однопользовательская модель не подходила для публичной семейной
ссылки.

**Причина:** исходная база не различала владельцев записей.

**Исправление:** введены `users`, `userId`, серверная идентификация и фильтрация
всех операций. Админка выводит только агрегаты.

**Статус:** исправлено в версии 6.

### FT-14. Редактор заметок утяжелял начальную загрузку

**Симптом:** TipTap входил в основной клиентский пакет, даже если пользователь
не открывал заметки.

**Причина:** редактор импортировался вместе с `flowtrack-app.tsx`.

**Исправление:** редактор вынесен в `rich-text-editor.tsx` и загружается
динамически при открытии заметки; добавлен контроль стартового пакета.

**Статус:** исправлено в версии 13.

### FT-15. Панель форматирования исчезала при прокрутке

**Симптом:** в длинной заметке приходилось возвращаться наверх для изменения
форматирования.

**Причина:** панель была частью прокручиваемого содержимого.

**Исправление:** панель закреплена в области редактора.

**Статус:** исправлено в версии 14.

### FT-16. Риск потери длинной заметки

**Симптом:** закрытие окна, сеть или перезагрузка могли оставить неотправленные
изменения без понятного статуса.

**Причина:** сохранение зависело от одного явного действия.

**Исправление:** добавлены автосохранение через 1,2 секунды покоя, очередь
записей, локальный черновик, повтор после сети, предупреждение перед закрытием и
явные состояния.

**Статус:** исправлено в версии 15.

### FT-17. Интерфейс не подходил всем размерам экрана

**Симптом:** стандартная плотность могла быть слишком мелкой или занимать
слишком много места.

**Причина:** существовал один размер элементов.

**Исправление:** добавлены компактный, комфортный и крупный режимы на
дизайн-токенах.

**Статус:** улучшено в версии 16.

### FT-18. Не было цельной тёмной темы и персонализации

**Симптом:** пользователь не мог выбрать тему, акцент, панель, стартовый экран
или степень анимаций.

**Причина:** настройки внешнего вида отсутствовали.

**Исправление:** добавлено меню персонализации с локальным хранением и ранним
применением параметров.

**Статус:** улучшено в версии 17.

### FT-19. Отметка привычки ощущалась медленной

**Симптом:** после нажатия календарь менялся с заметной задержкой.

**Причина:** интерфейс ждал запись, а затем повторно загружал весь набор данных.

**Исправление:** день меняется оптимистично, сервер получает идемпотентное
целевое состояние, повторное нажатие блокируется только на время записи, при
ошибке выполняется откат.

**Статус:** исправлено в версии 18.

### FT-20. Календарь выбивался из тёмной темы и занимал много места

**Симптом:** поверхности и состояния календаря были неравномерны, карточка была
слишком высокой.

**Причина:** календарь использовал старую плотность и неполный набор тёмных
токенов.

**Исправление:** сетка уплотнена, цвета переведены на общие поверхности,
добавлены полезные анимации с поддержкой минимального режима.

**Статус:** исправлено в версии 18.

### FT-21. На телефоне были потеряны настройки

**Симптом:** настройки не отображались, семь нижних пунктов слипались, а
плавающие кнопки перекрывали карточки.

**Причина:** широкое CSS-правило скрывало мобильный профиль; нижняя навигация не
имела приоритизации и безопасной зоны.

**Исправление:** оставлены четыре основных раздела и **«Ещё»**; поиск и профиль
вынесены в шапку; вторичные разделы и действия собраны в нижнем меню; исправлены
safe area, уведомления и мобильные окна.

**Статус:** исправлено в версии 19.

### FT-22. Для аналитики не хватало истории изменений

**Симптом:** текущий статус задачи не позволял достоверно определить старые
переносы и повторные открытия.

**Причина:** до версии 20 приложение сохраняло текущее состояние, но не все
переходы между состояниями.

**Исправление:** добавлены событийные таблицы, backfill доступных фактов и 13
триггеров.

**Ограничение:** старые переносы и повторные открытия невозможно восстановить
без исходных событий; интерфейс сообщает дату начала точного учёта.

**Статус:** фундамент исправлен в версии 20.

### FT-23. Удалённые записи оставались в аналитике

**Симптом:** после удаления привычек, задач и других исходных записей дашборд
продолжал показывать прежнюю активность; повторная загрузка не меняла числа.

**Причина:** версия 20 корректно обходила браузерный кэш, но намеренно строила
снимок по неизменяемой событийной истории, включая события уже удалённых
источников.

**Исправление:** события перед расчётом фильтруются по существующим активным
источникам; ответы API имеют явный режим `no-store`; клиент реагирует на
изменение исходных данных и предоставляет ручную кнопку обновления.

**Статус:** исправлено в версии 21.

## 6. Методология аналитики

FlowTrack не использует единый синтетический балл. Основные формулы:

| Метрика | Формула |
| --- | --- |
| Выполнение плана | Завершённые задачи из плана / задачи со сроком в прошедшей части периода |
| Выполнено в срок | Завершённые не позже действовавшего срока / завершённые со сроком |
| Фокус-время | Сумма завершённых свободных таймеров и Помодоро |
| Регулярность привычек | Засчитанные выполнения / ожидаемые выполнения |

Периоды выравниваются по календарю:

- неделя — понедельник–воскресенье;
- месяц — календарный месяц;
- квартал — календарный квартал;
- год — календарный год.

Текущий период заканчивается местной сегодняшней датой. Сравнение выполняется с
полным предыдущим календарным периодом.

Фильтр проекта применяется к задачам и фокус-времени. Привычки остаются
глобальными, поскольку сейчас не имеют связи с проектом.

Полная методология находится в
[спецификации аналитики](analytics.md).

## 9. Технические предупреждения и оставшийся долг

Это не подтверждённые пользовательские баги, а задачи следующих этапов:

1. «Аналитика» пока является дашбордом. Нет формирования, сохранения и
   экспорта отчёта в PDF или Excel.
2. Нет перехода из аналитической карточки к отфильтрованному списку исходных
   задач.
3. Точная история переносов и повторных открытий начинается только с версии
   20.
4. Привычки пока не привязаны к проектам.
5. Основной `flowtrack-app.tsx` остаётся крупным. TipTap уже вынесен из
   стартового пакета, но следующая оптимизация должна разделить основные
   разделы.
6. Нет полноценного E2E-набора, автоматически перетаскивающего канбан на
   компьютере и телефоне.
7. Нет автоматических ежедневных backup, мониторинга ошибок и метрик
   производительности.
8. Админка пока информационная: нет блокировки, удаления и управления ролями.
9. Нет PWA, офлайн-режима, APK и push-уведомлений.
10. Перед массовым запуском нужны нагрузочные тесты, политика хранения,
    поддержка, юридические процессы и инфраструктурный план.
